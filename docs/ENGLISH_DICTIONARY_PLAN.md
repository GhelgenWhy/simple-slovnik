# План: английский словарь как отдельная страница

> Статус: **реализовано полностью** (Фазы 1–5). Английский словарь —
> отдельная таблица `words_en` в `data/slovnik.db`, вкладка «🇬🇧 English»
> в главном окне, en_US проверка правописания, отдельные CSV и аудит.
> Ниже — исходный план, по которому велась реализация.
>
> Итог: +61 тест к набору (было 229, стало 290), чешская часть не
> изменена по поведению; синхронизация английского остаётся вне скоупа
> (слой БД уже `lang`-aware).

---

> Цель: добавить **полностью независимый английский словарь** в десктопное
> приложение. Это вторая «база» рядом с чешским словарём: те же CRUD,
> поиск, CSV-импорт/экспорт и внешний вид, но **никакого взаимодействия
> между английскими и чешскими словами** (по факту — 2 разные БД в одном
> приложении). Переключается вкладками: «🇨🇿 Чеський» и «🇬🇧 English».

---

## 0. Ключевые решения (что и почему)

| Вопрос | Решение | Обоснование |
|---|---|---|
| Где хранить английские слова | Отдельная таблица `words_en` в **том же** `data/slovnik.db` | Один файл для бэкапа, общий `sync_state`/`device_id`; таблицы полностью изолированы → чешские и английские слова не пересекаются |
| Как отличать головку записи | Новый «языковой» конфиг (`cs`→`cs`/`words`, `en`→`en`/`words_en`); колонка головки `en` вместо `cs` | Не переименовываем существующую схему чешского; английская головка хранится в своей колонке |
| Внутреннее имя поля головки | Оставляем `Word.cs` как «головка» для обоих языков (для en маппится из колонки `en`) | Минимальный разброс правок: `models.py`, UI и ~229 тестов не трогаются, т.к. пользователь `Word.cs` не видит |
| Английские проверки | Новый модуль `english.py` (`analyze_en`): минимум — «кириллица в en» + опц. английская орфография через `en_US` hunspell | Чешские правила (se/si, предлоги) к английскому **не применяются** |
| Синхронизация английского | **Вне скоупа первой версии.** Функции БД делаем `lang`-aware, чтобы добавить позже без переделки | Пользователь просил «просто отдельную страницу» |
| Мобильное приложение | **Вне скоупа** (только десктоп PySide6) | Отдельный follow-up: `tools/update_mobile_package.py` + Flet |

**Особый случай — id.** Таблицы `words` и `words_en` обе имеют
`AUTOINCREMENT`, поэтому `id=1` есть в обеих. Все CRUD-функции по id
(`get_word`, `update_word`, `delete_word`) обязаны знать `lang`, иначе
можно удалить/отредактировать запись из другой таблицы.

## 1. Фаза 1 — языковой конфиг + обобщение слоя БД (фундамент)

### Новый модуль `src/slovnik/lang.py`

```python
@dataclass(frozen=True)
class Language:
    code: str            # "cs" | "en"
    table: str           # "words" | "words_en"
    headword: str        # имя колонки головки: "cs" | "en"
    title: str           # "Cs" | "En" (для заголовков/поиска)
    emoji: str           # "🇨🇿" | "🇬🇧"
    csv_fields: tuple    # ("cs","uk","ru","pos","note") | ("en","uk","ru","pos","note")
    analyzer: Callable   # analyze_cs | analyze_en

LANGUAGES = {"cs": Language(...), "en": Language(...)}
```

### `src/slovnik/db.py`

- Добавить схему `words_en` (зеркало `words`, но головка `en`) + частичный
  уникальный индекс `idx_words_en_live ON words_en(en COLLATE NOCASE) WHERE deleted=0`.
- `init_db`/`_migrate` создают **обе** таблицы (идемпотентно; чешская часть
  не меняется).
- Добавить `lang: str = "cs"` в функции и выводить `table`/`headword` из
  `LANGUAGES[lang]`. Затронутые функции: `add_word`, `get_word`,
  `update_word`, `delete_word`, `list_words`, `iter_words`, `search_words`,
  `dirty_rows`, `clear_dirty`, `stamp_device_id`, `mark_all_dirty`,
  `apply_synced_row`, `_row_to_word`.
- `_row_to_word`: для `en` читает `row["en"]` в `Word.cs` (головка остаётся
  внутренним полем `cs`). `apply_synced_row` матчит по головке языка
  (`cs`/`en`) и пишет её в свою колонку.
- Все дефолты `lang="cs"` → существующие вызовы и тесты работают без изменений.

### Тесты

- `tests/test_english_db.py`: CRUD en (add/get/update/delete/soft-delete),
  поиск по `en/uk/ru`, уникальность головки (NOCASE), изоляция — английская
  запись не видна в `list_words(lang="cs")` и наоборот.
- Существующие чешские тесты должны остаться зелёными (регрессия).

## 2. Фаза 2 — английская проверка + словарь

### Новый модуль `src/slovnik/english.py`

- `analyze_en(text, checker=None) -> list[Issue]` — переиспользует `Issue`
  из `czech.py` (или вынести `Issue`/`KIND_LABELS` в общий модуль, чтобы не
  тянуть чешские правила).
- Минимум правил: **кириллица в `en`** (тот же класс «alphabet»). Дальше —
  расширяемо (типовые ошибки: `i`/`e`, двойные буквы и т.п.) без влияния на
  чешский.

### Английский hunspell-словарь (опционально в этой же фазе)

- `dicts/en_US/en_US.aff` + `en_US.dic` (LibreOffice dictionaries, MPL-2.0).
- `SpellChecker` уже принимает `dict_dir`, но имена файлов захардкожены как
  `cs_CZ.aff/.dic` — заменить на вывод из имени каталога
  (`self.dict_dir.name` → `en_US`), чтобы работали оба.
- `analyze_en` подключает орфографию через `SpellChecker(dict_dir=dicts/en_US)`.

### Тесты

- `tests/test_english.py`: кириллица в `en`, орфография (`aple` → `apple`),
  что чешские правила (se/si) к английскому не применяются.

## 3. Фаза 3 — вкладки в UI

### Извлечь `src/slovnik/ui/vocabulary_page.py`

- Новый виджет `VocabularyPage(QWidget)` с параметром `lang: Language`.
  Переносит из `MainWindow` всю логику списка: поиск, список, кнопки
  ➕/✏️/🗑️/✅Проверить/📥/📤 CSV, debounced search, `_format_word`,
  `_refresh_list`, `_selected_id`, обработчики CRUD/проверки/CSV.
  Все строки локализуются через `lang`:
  - плейсхолдер поиска: «… cs / uk / ru» ↔ «… en / uk / ru»;
  - `_format_word`: флаг головки `lang.emoji` (🇨🇿/🇬🇧);
  - кнопка проверки вызывает `lang.analyzer`.
- Кнопки синхронизации (⬇ Pull / ⬆ Push / 🔗 Sync…) остаются **только** в
  чешской странице (английской синхронизации пока нет).

### `src/slovnik/ui/main_window.py` → оболочка

- `MainWindow` становится оболочкой: `QTabWidget` с двумя
  `VocabularyPage("cs")` и `VocabularyPage("en")`, меню «Вигляд» (always-on-top),
  статус-бар. Синхронизация — по-прежнему поверх чешской БД (можно оставить
  её в чешской странице или перенести в оболочку — план: в чешской странице,
  чтобы не менять семантику).
- Клавиши (Ctrl+F/Ctrl+N/Del) должны работать для **активной** вкладки.

### `src/slovnik/ui/word_dialog.py`

- Параметр `lang`; подпись головки = `lang.title` («🇨🇿 Česky *:» ↔
  «🇬🇧 English *:»), валидация при сохранении = `lang.analyzer`,
  «жёсткие» виды ошибок задаются языком (для en — только `alphabet`).
- `add_word`/`get_word`/`update_word` вызываются с `lang=...`.

### Тесты

- `tests/test_main_window_english.py` / `test_vocabulary_page.py`: наличие двух
  вкладок, переключение, добавление/редактирование/удаление английской записи
  не трогает чешскую, подпись и флаг в списке для en.

## 4. Фаза 4 — CSV и аудит БД

### `src/slovnik/import_export.py`

- `export_csv`/`import_csv` получают `lang="cs"`: заголовок CSV берётся из
  `lang.csv_fields`; для en колонка `en` маппится в `Word.cs`.
- Дефолт `"cs"` — чешские тесты без изменений.

### `src/slovnik/db_check.py`

- Флаг `--lang {cs,en}`: аудит английского запускает `analyze_en`, проверяет
  поле `en` (кириллица, пустота, пробелы), дубликаты — по `en`. Чешский
  аудит не должен бегать по таблице en и наоборот.
- (Если хотите «всё в одном отчёте» — добавить `--lang all`; план по умолчанию:
  отдельный прогон на язык.)

### Тесты

- `tests/test_import_export.py` (en round-trip с заголовком `en`),
  `tests/test_db_check.py` (`--lang en`).

## 5. Фаза 5 — документация и финальная проверка

- `README.md`: секция «Английский словарь», обновить схему данных (таблица
  `words_en`), таблицу фич, FAQ (что чешские и английские слова разделены).

- Ручная проверка: переключение вкладок, CRUD/поиск/CSV/проверка в обеих,

  открывается и мигрирует без потери данных.

## 7. Вне скоупа (отмечено, чтобы не делать случайно)

- Синхронизация английского через `server/` и `slovnik.sync`.
- Английский словарь в мобильном APK (`mobile/`).
- Любые перекрёстные ссылки чешский ↔ английский (требование: ничто не
  взаимодействует).
- Миграция/переименование существующих колонок `words` (не трогаем чешскую БД).
