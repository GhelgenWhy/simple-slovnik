## 4. Этап B — закрытие ошибок, влияющих на данные

### B1. Добавление слова на телефоне

Кнопка «+» вызывает `_open_editor(None)`. Сохранение и выход сбрасывают состояние редактора согласованно; открытие нового слова не наследует id предыдущего.

Приёмка: существующее слово → редактирование → назад → «+» → сохранение. В БД две записи, прежняя не изменена. Проверить также переход после удаления и отмену нового слова.

### B2. Подтверждение отправленных версий

Добавить локальную ревизию записи с идемпотентной миграцией обеих таблиц. Увеличивать её при каждом локальном изменении, включая удаление. Push захватывает снимок `(id, revision)` и содержимое. После подтверждённого ответа снимается dirty только у записей с совпадающей отправленной ревизией. Общий `clear_dirty()` в этом пути исключить.

Обработку серверного конфликта также связать со снимком: если запись изменилась за время запроса, новый локальный вариант должен остаться pending и не быть затёрт ответом на старую версию.

Приёмка: добавление, изменение, удаление во время сетевого запроса; конфликтный ответ при новой правке; потеря ответа и повторный Push. Новые ревизии остаются dirty, повторная отправка идемпотентна.

### B3. Переименование

Для первого исправления сохранить идентичность по headword: в одной транзакции создать tombstone старого имени и обновить/создать новую активную запись. Любой конфликт уникальности нового имени должен откатить всю операцию. Имена, отличающиеся только регистром, обработать отдельно без лишнего tombstone.

Приёмка: обычное переименование, офлайн-переименование, несколько переименований подряд, уже существующее новое имя, rename с конкурентной правкой на другом устройстве. Старое слово не возвращается после Push/Pull.

Переход на UUID записей рассматривать позднее как отдельную миграцию протокола, если потребуется сохранять непрерывную историю идентичности. Не совмещать его без необходимости с первым исправлением.

### B4. Порядок версий и соединения

Миллисекунды SQLite не гарантируют разные LWW-ключи для быстрых записей. Обеспечить строго возрастающее время версии для локальных изменений одной записи даже при одинаковом времени/откате часов; локальная ревизия сама по себе не меняет действующий LWW wire-format. Сохранить сравнимый канонический формат UTC для старых клиентов.

Закрывать SQLite connections явно. Добавить проверку освобождения файла на Windows. Не менять формат временных строк без проверки совместимости существующих данных.

После каждой правки общего ядра выполнить `tools/update_mobile_package.py` и проверку копий, как требует AGENTS.md.

## 5. Этап C — надёжная чешская синхронизация

1. **Пагинация:** каждый принятый сервером write получает возрастающий change sequence. Обычный id строки недостаточен: редактирование старого слова тоже должно продвигать последовательность. Сделать API продолжения страниц и фиксировать границу снимка. Клиент подтверждает обработанную страницу, а не текущее время при неполной выдаче. Проверить >10 000 строк, одинаковые timestamps и обновления между страницами.
2. **Совместимость:** сохранить старые чешские endpoints. Новому клиенту дать version/capabilities и новый cursor API. Для legacy Pull определить безопасное поведение при переполнении, исключающее успешную неполную выдачу с продвижением курсора. Не оставлять старые клиенты молча теряющими данные.
3. **Смена/восстановление сервера:** хранить постоянный server UUID и generation, а на клиенте состояния по серверу и языку. Добавить явное действие полной выгрузки с понятным предварительным результатом. Изменение URL/пустая серверная БД не должно незаметно превращаться в успешный Push с нулём строк.
4. **Полная выгрузка:** согласовать отправку активных записей и tombstones, сохранить прежние timestamps и авторство. Прежде чем считать одну БД источником восстановления, сверить pending-правки на остальных устройствах. Не очищать существующий сервер ради bootstrap.
5. **Ошибки:** валидировать schema ответов; не снимать dirty и не двигать cursor при ошибках. Sync-поток завершать через `try/finally`, возвращать кнопки в рабочее состояние. Исключить параллельные sync-запуски для одной БД.
6. **Архив конфликтов:** сохранять проигравшие версии в обоих направлениях. Уточнить срок хранения; подготовить просмотр/восстановление на клиенте. В интерфейсе описывать защиту pending на Pull и LWW на Push без обещания безусловной победы сервера.

Приёмка: два независимых клиента, UTF-8, повторный Push, tombstones, конфликт, неверный токен, timeout, обрыв ответа, заполнение нового сервера, восстановление, >10 000 строк. Данные сходятся либо остаются явно pending/конфликтными, без скрытого пропуска.

## 6. Развёртывание на `2.27.98.151`

### Подготовка

- Сохранить конфигурацию действующего Tailscale Serve и перечень текущих сервисов; обеспечить доступ по SSH после изменений.
- Проверить выбранный Python и доступность venv. Вывод dpkg-query в диагностике не подтвердил пригодность venv; выполнить пробное создание окружения. При необходимости установить пакет venv, соответствующий интерпретатору. Не полагаться автоматически на Python 3.13 при текущем default 3.14.7.
- Настроить синхронизацию времени через одну выбранную NTP-службу; проверить `NTPSynchronized=yes`. Это снижает риски LWW, но не заменяет исправление порядка версий.
- Создать системного пользователя `slovnik-sync` без login shell. Создать `/opt/slovnik-sync`, `data`, каталог релизов и резервных копий.
- Установить проверенные версии FastAPI/uvicorn из зафиксированного набора зависимостей в отдельное venv. Приложение оставить standalone, без Qt и зависимости от desktop-установки.

### Конфигурация

В `/opt/slovnik-sync/.env` сохранить `SLOVNIK_DB=/opt/slovnik-sync/data/server.db` и новый случайный `SLOVNIK_TOKEN`. Права файла 600; токен не выводить в отчёт/логи и не помещать в репозиторий. Если обнаружится прежняя установка, сначала проверить её токен и данные, а не заменять автоматически.

Подготовить unit в репозитории и установить как `/etc/systemd/system/slovnik-sync.service`:

```ini
[Unit]
Description=Slovnik sync server
After=network-online.target
Wants=network-online.target

[Service]
User=slovnik-sync
Group=slovnik-sync
WorkingDirectory=/opt/slovnik-sync
EnvironmentFile=/opt/slovnik-sync/.env
ExecStart=/opt/slovnik-sync/venv/bin/uvicorn app:app --host 127.0.0.1 --port 8000
Restart=on-failure
RestartSec=3
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/opt/slovnik-sync/data
UMask=0077

[Install]
WantedBy=multi-user.target
```

Проверить ограничения unit на тестовом запуске и адаптировать ReadWritePaths, если исправленный сервер хранит дополнительные файлы. Код и venv могут принадлежать root, writable data — пользователю сервиса.

После локальной проверки добавить отдельный endpoint:

```bash
tailscale serve --bg --https=8443 http://127.0.0.1:8000
tailscale serve status
```

Подтвердить, что существующий HTTPS 443 → 5985 сохранился. Не публиковать 8000 на `0.0.0.0`; обеспечить доступ нужных устройств к 8443 через tailnet ACL. Docker для Slovník не требуется.

### Бэкапы, обновление и откат

Добавить systemd timer ночного SQLite backup API/`.backup`, срок хранения 30 дней и проверку integrity копии. Резервные копии держать с ограниченными правами; периодически переносить на другое устройство. Раз в установленный период проверять восстановление в отдельную БД.

Обновлять через отдельный каталог релиза: загрузка → проверка версии/хеша → резервная копия БД → переключение → restart → health/auth/TLS проверки. Хранить предыдущий код и окружение. При несовместимой миграции откат к старому коду требует согласованной БД; восстановление старой копии может потерять новые записи, поэтому сначала сохранить состояние после неудачного релиза.

## 10. Что считать закрытием проекта улучшений

Критические сценарии аудита больше не воспроизводятся; общий тестовый запуск включает mobile. Сервер существует и доступен по проверенному TLS URL, не мешает Obsidian, защищён токеном, имеет проверенный бэкап и порядок восстановления. APK соответствует исходникам и сохраняет данные при обновлении. Чешские и английские слова независимо проходят полный цикл ПК ↔ телефон, а ошибки сети не скрывают pending-правки.

Работы выполнять последовательными изменениями с отдельной приёмкой A–F; не объявлять завершённой мобильную приёмку по успешной компиляции APK или одним только unit-тестам.
