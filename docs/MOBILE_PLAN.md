# План: мобильное приложение (APK) + синхронизация через свой сервер

> Статус: **план, не реализовано**. Документ — отправная точка для будущих
> сессий: цели, выбор технологий, схема синхронизации, фазы работ и риски.
> Ключевое требование: нативный APK (не веб-приложение), синхронизация
> через собственный сервер, доступный только в Tailscale (по образцу
> Obsidian Self-hosted LiveSync).

---

## 1. Цели и не-цели

**Цели**
- Полноценное Android-приложение (APK), устанавливаемое на телефон.
- Оффлайн-первое: всё работает без сети; синхронизация — фон/кнопка.
- Двусторонняя синхронизация словаря между ПК (этот PySide6-проект) и
  телефоном через свой сервер в Tailscale.
- Повторное использование уже написанной логики: `db.py` (схема/CRUD),
  `czech.py` (se/si + предлоги), `spellcheck.py` (pure-бэкенд).

**Не-цели (сознательно)**
- iOS (можно добавить позже тем же стеком, но не в первой версии).
- Публичный интернет-доступ к серверу — только tailnet.
- Real-time «живая» синхронизация с подпишись-на-изменения: для
  персонального словаря хватает pull/push по запросу + при старте.

## 2. Выбор фреймворка для APK

| Вариант      | Плюсы                                    | Минусы                                   |
|--------------|------------------------------------------|------------------------------------------|
| **Flet** (рекомендуется) | Python; красивый Material-UI; `flet build apk`; переиспользуем `db.py`/`czech.py` почти как есть | Зависимость от Flutter SDK при сборке; молодость платформы |
| Kivy + Buildozer | Зрелый, чистый Python, APK полностью локально | Свой некрастивый UI; сборка только из Linux/WSL; много ручной возни |
| Flutter/Dart | Лучший UX и производительность            | Полная переписка логики (db/czech/spellcheck) на Dart — двойная поддержка таблицы глаголов |
| React Native / Kotlin | Нативно                    | Полная переписка + JS/Android-тулинг     |

**Рекомендация: Flet.** Словарь — это списки, формы и поиск, ровно то, что
Flet делает из коробки; при этом весь «мозг» (проверки чешского) остаётся
на Python и общим для ПК и телефона.

### Обязательный спайк (Фаза 0, ~1 сессия)
Перед большой работой проверить на реальном устройстве:
1. `flet build apk` собирается из Windows (или WSL2) и ставится на телефон.
2. `sqlite3` работает внутри APK (Flet упаковывает Python-рантайм).
3. Ассет `dicts/cs_CZ/cs_CZ.dic` (~3 МБ) читается из пакета, pure-бэкенд
   `SpellChecker` загружается за приемлемое время (< 2 c).
4. HTTP-клиент (`requests`/`httpx`) внутри APK достучался до тестового
   URL (нужен для синхронизации).
5. `python-Levenshtein` под ARM не ставится → работает difflib-fallback
   (он уже есть в `spellcheck.py`) — замерить скорость подсказок.

Если Flet проваливает 2–3 пункта спайка — откат на Kivy+Buildozer
(пункты проверяются там почти так же).

## 3. Архитектура синхронизации

```
┌──────────────┐   Tailscale (WireGuard, шифровано)   ┌──────────────────┐
│  ПК (PySide6)│ ───────────────────────────────────► │  Сервер (VPS/    │
│  slovnik.db  │ ◄─────────────────────────────────── │  home-server)    │
└──────────────┘            HTTP + JSON               │  FastAPI+SQLite  │
       ▲                                                └────────▲─────────┘
       │ same sync client (pure Python)                          │
┌──────┴───────┐                                             tailnet only,
│ Телефон (APK)│                                             никакой публичной
│  slovnik.db  │                                             экспозиции
└──────────────┘
```

### Модель: last-write-wins per word + tombstones

Слова — маленькие независимые записи; для одного-двух пользователей
конфликты редки. Берём простую и надёжную модель:

- Каждая строка получает `updated_at` (UTC, проставляет клиент) и
  `deleted` (0/1, tombstone) + `device_id` (для диагностики).
- **Push**: клиент отправляет строки, изменённые после своего
  `last_sync_at`. Сервер применяет LWW: перезаписывает свою версию, если
  присланная `updated_at` новее; иначе возвращает «конфликт» со своей
  версией (клиент показывает пользователю 2 варианта на выбор).
- **Pull**: клиент запрашивает `GET /sync/pull?since=last_sync_at`,
  получает чужие изменения + tombstones, применяет LWW локально.
- `UNIQUE(cs)` при слиянии: если при pull приходит слово, дублирующее
  локальное по `cs` — слить в более свежее, оставить один id.

### Почему не CouchDB (как в Obsidian LiveSync)

CouchDB даёт готовую репликацию с ревизиями — но Python-клиента под
Android для него нет (pouchdb — это JS), пришлось бы писать свой
репликатор поверх HTTP API — сопоставимо по трудозатратам с LWW-сервером
на FastAPI, но с меньшим контролем. Вариант оставлен как «план B»:
наш JSON-row-формат легко конвертируется в couch-документы, сервер можно
заменить, не трогая клиентов.

### Сервер (FastAPI, ~150 строк)

```
POST /sync/push  {device_id, last_sync_at, rows: [...]} → {applied, conflicts}
GET  /sync/pull?since=ISO8601 → {server_time, rows: [...]}
GET  /health
```
- Auth: один статический Bearer-токен в конфиге (в tailnet этого
  достаточно; без публичного экспоуза).
- Хранилище: тот же SQLite (`server.db`), таблица `words` без UNIQUE —
  сервер не судья, а брокер.
- Деплой: `docker-compose.yml` (образ python:3.12-slim + volume для
  db) на любой домашний сервер/VPS; в Tailscale машина уже сидит —
  достаточно `ALLOWED_HOST` = MagicDNS-имя вида
  `http://slovnik:8000` (или tailscale serve для TLS).
- Бэкап: nightly `cp server.db` + `sqlite3 .dump` в git-репозиторий.

### Клиент синхронизации (общий для ПК и APK)

Новый модуль `src/slovnik/sync.py` (pure Python, без Qt):

```
class SyncClient:
    def __init__(self, db_path, server_url, token, device_id)
    def push(self) -> SyncResult   # отправить свои изменения
    def pull(self) -> SyncResult   # забрать чужие, применить LWW
    def sync(self) -> SyncResult   # pull → push → сохранить last_sync_at
```
- Прогресс/ошибки — через колбэк, чтобы ПК показывал в статус-баре,
  а APK — snackbar.
- Состояние: таблица `sync_state(key TEXT PRIMARY KEY, value TEXT)` в
  той же БД (`last_sync_at`, `device_id`).
- Миграция `db.py`: `ALTER TABLE words ADD COLUMN deleted …`,
  `device_id …`; `updated_at` уже есть — только обеспечить UTC.

## 4. Мобильный UI (Flet) — экраны

1. **Список + поиск** (главный): строка поиска, ListView с
   `cs — uk/ru`, тап → карточка слова.
2. **Карточка слова**: все поля, кнопки Править / Удалить / Проверить.
3. **Редактор**: те же поля, что в WordDialog, + кнопка «Проверить cs»
   (переиспользуем `analyze_cs` — выдаёт те же подсказки se/si).
4. **Синхронизация**: страница настроек (URL сервера, токен, device_id)
   + кнопка «Синхронизировать сейчас» + автосинк при старте (опция).
5. Быстрое добавление из буфера обмена (long-press → «Добавить в Slovníк»
   через share intent — вторая итерация).

## 5. Сборка APK

- `flet create` → приложение тянет `src/slovnik/{db,czech,spellcheck,sync}.py`
  как общий пакет (git submodule / monorepo-папка `mobile/`).
- Ассеты: `dicts/cs_CZ/*` (упаковать в APK).
- Подпись release-key, `flet build apk --release`; на телефоне —
  «установка из неизвестных источников».
- Windows-хост: сборка через WSL2, если Flutter потребует Linux-тулчейн
  (проверить в спайке).
- Обновление APK — просто новая установка поверх (свои данные в app
  storage не трогаются).

## 6. Фазы работ (по сессиям/токенам)

| Фаза | Содержание                                                  | Оценка        |
|------|-------------------------------------------------------------|---------------|
| 0    | Спайк Flet на устройстве (5 пунктов выше)                   | 1 сессия      |
| 1    | Миграция схемы (`deleted`, `device_id`, UTC) + `sync.py` с тестами на моках | 1–2 сессии |
| 2    | FastAPI-сервер + docker-compose + ручной тест curl           | 1 сессия      |
| 3    | Мобильный UI: список/поиск/редактор/проверка cs (переиспольз. `czech.py`) | 2–3 сессии |
| 4    | Интеграция sync в APK + на ПК (меню «Синхронизировать»)      | 1–2 сессии   |
| 5    | Полировка: иконка, splash, share-intent, бэкапы сервера      | 1 сессия      |

Итого ~7–10 полноценных сессий. Фазы 1–2 не зависят от мобильного UI и
приносят пользу уже настольному приложению (бэкап на сервер).

## 7. Риски и меры

- **Flet не соберётся / sqlite3 нет в APK** → спайк Фазы 0 провалится
  быстро, откат на Kivy+Buildozer (логика не меняется, только UI-слой).
- **Большие словари в pure-бэкенде на телефоне** → загрузка ~3 МБ в
  память; замерить в спайке; при тормозах — грузить лениво и только для
  экрана проверки.
- **Конфликты правок с двух устройств** → редкий случай; UI показывает
  обе версии, пользователь выбирает; сервер хранит проигравшую версию
  в `conflicts`-таблице 30 дней.
- **Потеря сервера** → данные целиком живут на клиентах; сервер
  пересобирается первым pull-ом с ПК.
- **Сон телефона во время sync** → sync короткий (сотни строк);
  на Android запрашивать wakelock не требуется.
