## 0. Что уже сделано (отчёт о реализации Фаз 1–2)

**Фаза 1 — схема + клиент (готово, покрыто тестами):**
- Миграция `db.py` (idempotent, гонялась на копии реальной БД):
  - колонки `words.deleted` (tombstone), `words.device_id`, `words.dirty`;
  - `sync_state(key, value)` — курсор `last_sync_at` + `device_id`;
  - `sync_conflicts` — локально проигравшие версии (будущий UI конфликтов);
  - старый табличный `UNIQUE(cs)` перестроен в частичный уникальный индекс
    `idx_words_cs_live … WHERE deleted = 0` — tombstone не мешает
    повторно добавить то же слово; если в старой БД есть дубликаты,
    индекс откладывается (БД всё равно открывается, дубликаты ловит
    `db_check`).
- `updated_at` теперь UTC с микросекундами
  (`strftime('%Y-%m-%d %H:%M:%f','now')`): секундная точность ломала LWW
  при «добавил и тут же удалил в ту же секунду». Старые строки
  сортируются корректно (строковое сравнение).
- `delete_word` теперь **soft delete** (tombstone) — из UI исчезает,
  для синка остаётся; `hard=True` удаляет физически.
- `sync.py` — `SyncClient` (pure Python, только stdlib `urllib` — без
  зависимостей, важно для APK): `push()` / `pull()` / `sync()`,
  прогресс/ошибки через колбэк, Bearer-токен, понятные сообщения об
  ошибках (bad token, нет сети, таймаут).
- Отслеживание изменений — по флагу `dirty` (устойчиво к расхождению
  часов клиент/сервер), а не «изменено после last_sync_at».
- Слияние — LWW по ключу `(updated_at, device_id)`, идентичность слова —
  `cs` (NOCASE); локальные id не участвуют в матче. Проигравшая «грязная»
  локальная версия сохраняется в `sync_conflicts` перед перезаписью.
- Pull-курсор с 5-секундным перекрытием (`PULL_OVERLAP_SECONDS`) —
  страховка от гонки «строка закоммичена между SELECT и чтением часов
  сервера»; повторное применение строк идемпотентно (LWW).
- Тесты: миграция legacy-схемы, LWW/tombstones на уровне `db.py`,
  end-to-end два клиента через живой uvicorn-сервер (конфликты,
  tombstone-пропагация, токен, офлайн), API сервера (fail-closed без
  токена, курсор, идемпотентность).

**Фаза 2 — сервер (готово, проверено curl-ом):**
- `server/app.py` — FastAPI-брокер (~250 строк): `POST /sync/push`,
  `GET /sync/pull?since=…`, `GET /health`; LWW по `cs`, проигравшие
  версии — в таблице `conflicts` (чистка старше 30 дней); tombstones
  хранятся, не удаляются; идемпотентный re-push (skipped).
- Auth: статический `Bearer SLOVNIK_TOKEN`; **без настроенного токена
  сервер отвечает 503 на всё кроме /health (fail closed)**.
- Хранилище: `server.db` (SQLite, WAL), таблица `words` **без UNIQUE**
  (сервер — брокер, не судья), курсор pull — по `received_at`
  (серверные часы, микросекунды).
- Деплой: **развернут на `ghelgenserver` (Debian 13): systemd-сервис
  `slovnik-sync` на `127.0.0.1:8000` + `tailscale serve --https=8443`;
  URL для клиентов `https://ghelgenserver.taile8591e.ts.net:8443`,
  токен в `/opt/slovnik-sync/.env`** (проверено curl-ом: 401 без токена,
  push/pull UTF-8, LWW-конфликт). Docker-вариант тоже готов:
  `server/Dockerfile` + `server/docker-compose.yml` (volume `/data`).
  Extra для установки: `pip install -e ".[sync-server]"`.

Отличия от плана ниже (все — в сторону упрощения/надёжности): dirty-флаг
вместо «changed since last_sync_at»; pull-перекрытие; идентичность по
`cs` вместо id; device_id как tie-break LWW. Остальное — как в плане.

**Фаза 4 (desktop-часть) — готово:**
- Кнопки **⬇ Pull / ⬆ Push** в нижней панели главного окна + диалог
  «🔗 Sync…» (URL + токен в QSettings: `sync/server_url`, `sync/token`).
- Пулл/пуш — разовые, по клику, в фоновом QThread (UI не замирает),
  результат — в статус-баре, список обновляется сам.
- Семантика конфликтов (решение пользователя, проще UI выбора версий):
  **Pull = выигрывает устройство** — строки с непушенными локальными
  правками всегда старше серверных (`apply_synced_row(keep_dirty_local=
  True)`), остаются `dirty` до следующего Push.
  **Push = выигрывает сервер** — присланную сервером конфликтную версию
  клиент сразу применяет локально (`push(accept_server_conflicts=True)`),
  проигравшая правка сохраняется в `sync_conflicts` для восстановления.
- Тесты: оба режима на уровне db и клиента (два устройства через живой
  сервер), UI-тесты кнопок против локального uvicorn-сервера.

## 1. Цели и не-цели

**Цели**
- Полноценное Android-приложение (APK), устанавливаемое на телефон.
- Оффлайн-первое: всё работает без сети; синхронизация — фон/кнопка.

**Не-цели (сознательно)**
- iOS (можно добавить позже тем же стеком, но не в первой версии).
- Публичный интернет-доступ к серверу — только tailnet.
- Real-time «живая» синхронизация с подпишись-на-изменения: для
  персонального словаря хватает pull/push по запросу + при старте.

## 3. Архитектура синхронизации

```
┌──────────────┐   Tailscale (WireGuard, шифровано)   ┌──────────────────┐
│  ПК (PySide6)│ ───────────────────────────────────► │  Сервер (VPS/    │
│  slovnik.db  │ ◄─────────────────────────────────── │  home-server)    │
└──────────────┘            HTTP + JSON               │  FastAPI+SQLite  │
       ▲                                                └────────▲─────────┘
       │ same sync client (pure Python)                          │
┌──────┴───────┐                                             tailnet only,
│ Телефон (APK)│                                             никакой публичной
│  slovnik.db  │                                             экспозиции
└──────────────┘
```

### Модель: last-write-wins per word + tombstones

Слова — маленькие независимые записи; для одного-двух пользователей
конфликты редки. Берём простую и надёжную модель:

- Каждая строка получает `updated_at` (UTC, проставляет клиент) и
  `deleted` (0/1, tombstone) + `device_id` (для диагностики).
- **Push**: клиент отправляет строки, изменённые после своего
  `last_sync_at`. Сервер применяет LWW: перезаписывает свою версию, если
  присланная `updated_at` новее; иначе возвращает «конфликт» со своей
  версией (клиент показывает пользователю 2 варианта на выбор).
- **Pull**: клиент запрашивает `GET /sync/pull?since=last_sync_at`,
  получает чужие изменения + tombstones, применяет LWW локально.
- `UNIQUE(cs)` при слиянии: если при pull приходит слово, дублирующее
  локальное по `cs` — слить в более свежее, оставить один id.

### Почему не CouchDB (как в Obsidian LiveSync)

CouchDB даёт готовую репликацию с ревизиями — но Python-клиента под
Android для него нет (pouchdb — это JS), пришлось бы писать свой
репликатор поверх HTTP API — сопоставимо по трудозатратам с LWW-сервером
на FastAPI, но с меньшим контролем. Вариант оставлен как «план B»:
наш JSON-row-формат легко конвертируется в couch-документы, сервер можно
заменить, не трогая клиентов.

### Сервер (FastAPI, ~150 строк)

```
POST /sync/push  {device_id, last_sync_at, rows: [...]} → {applied, conflicts}
GET  /sync/pull?since=ISO8601 → {server_time, rows: [...]}
GET  /health
```
- Auth: один статический Bearer-токен в конфиге (в tailnet этого
  достаточно; без публичного экспоуза).
- Хранилище: тот же SQLite (`server.db`), таблица `words` без UNIQUE —
  сервер не судья, а брокер.
- Деплой: `docker-compose.yml` (образ python:3.12-slim + volume для
  db) на любой домашний сервер/VPS; в Tailscale машина уже сидит —
  достаточно `ALLOWED_HOST` = MagicDNS-имя вида
  `http://slovnik:8000` (или tailscale serve для TLS).
- Бэкап: nightly `cp server.db` + `sqlite3 .dump` в git-репозиторий.

### Клиент синхронизации (общий для ПК и APK)

Новый модуль `src/slovnik/sync.py` (pure Python, без Qt):

```
class SyncClient:
    def __init__(self, db_path, server_url, token, device_id)
    def push(self) -> SyncResult   # отправить свои изменения
    def pull(self) -> SyncResult   # забрать чужие, применить LWW
    def sync(self) -> SyncResult   # pull → push → сохранить last_sync_at
```
- Прогресс/ошибки — через колбэк, чтобы ПК показывал в статус-баре,
  а APK — snackbar.
- Состояние: таблица `sync_state(key TEXT PRIMARY KEY, value TEXT)` в
  той же БД (`last_sync_at`, `device_id`).
- Миграция `db.py`: `ALTER TABLE words ADD COLUMN deleted …`,
  `device_id …`; `updated_at` уже есть — только обеспечить UTC.

## 7. Риски и меры

- **Flet не соберётся / sqlite3 нет в APK** → спайк Фазы 0 провалится
  быстро, откат на Kivy+Buildozer (логика не меняется, только UI-слой).
- **Большие словари в pure-бэкенде на телефоне** → загрузка ~3 МБ в
  память; замерить в спайке; при тормозах — грузить лениво и только для
  экрана проверки.
- **Конфликты правок с двух устройств** → редкий случай; UI показывает
  обе версии, пользователь выбирает; сервер хранит проигравшую версию
  в `conflicts`-таблице 30 дней.
- **Потеря сервера** → данные целиком живут на клиентах; сервер
  пересобирается первым pull-ом с ПК.
- **Сон телефона во время sync** → sync короткий (сотни строк);
  на Android запрашивать wakelock не требуется.
